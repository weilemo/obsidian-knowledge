## 0. 重要提示（已接管）

- 当前 A100 集群已由 Slurm 接管：请使用 `sbatch` / `srun` 提交作业，不要在登录 shell 里长期裸跑占用 CPU/GPU。
- `sinfo` 的 `idle` 表示 Slurm 视角“可调度”，但提交前仍建议自查 `nvidia-smi`（尤其是你在某台机器上做过手工调试/临时进程时）。
- 如需运行“常驻服务”（对外 Web/API、后台守护进程），请先与管理员确认部署方式；计算节点默认用于跑作业，不建议作为长期服务宿主。

## 1. 核心概念：存储与分区映射（最容易出错）

| 数据存放位置 | 路径特征 | 适用场景 | 应选分区（Partition） |
|---|---|---|---|
| 全节点共享盘 | `/mnt` | 代码、通用数据集、模型输出 | `a100_global`（默认/推荐） |
| 本机本地盘 | `/data` | 强依赖本地高 IO 的数据 | `a100_local_<节点名>` |
| 本机扩展盘 | `/data2` | 部分节点的扩展存储 | `a100_local_<节点名>` |

注意：
- 节点 `A100-0371-23100` 没有 `/data2`。
- 如果依赖 `/data` 或 `/data2`，务必指定 `a100_local_<节点名>` 或 `--nodelist=<节点名>`，否则可能被调度到没有该数据的机器上。

## 1.5 项目（Account）与默认 sandbox

- 每个作业都应该显式指定项目账号：`--account <project_id>`
- 若未指定，系统会自动将作业归入 `sandbox`（低优先级 + 严限制，适用于探索/兼容场景）

### 1.5.1 优先级（QOS 档位）

- `default < important < urgent`
- 管理员会为每个项目账号设置默认档位（DefaultQOS）。

### 1.5.2 提交作业：推荐写法

```bash
# 正式项目
sbatch --account cv_project_a run.sbatch
srun  --account cv_project_a -p a100_global --gres=gpu:1 --pty bash -l

# 不写 --account 会进入 sandbox（低优先级）
sbatch run.sbatch

# urgent 项目中提交“不那么急”的任务：显式降到 important/default
sbatch --account urgentproj --qos important run.sbatch
sbatch --account urgentproj --qos default run.sbatch
```

注意：
- 不建议用户自行“升档”（例如在 default 项目里提交 `--qos urgent`），通常会被拒绝（InvalidQOS）。
- 如果你没有加入某个项目账号（无 association），提交会失败（InvalidAccount），请联系管理员分配。

自查（看 Account/QOS 是否正确）：

```bash
squeue -u $USER -o "%.10i %.16a %.10q %.10T %.20R"
```

## 2. 常用命令速查表（Cheatsheet）

| 动作 | 命令 | 说明 |
|---|---|---|
| 查看节点/分区 | `sinfo -N -l` | 查看节点状态（Idle/Alloc/Down） |
| 查看作业队列 | `squeue -u $USER` | 查看自己的作业 |
| 提交作业 | `sbatch run.sbatch` | 异步提交脚本 |
| 取消作业 | `scancel <jobid>` | 终止作业 |
| 交互调试 | `srun ... --pty bash -l` | 申请资源并进入交互 shell |

## 3. 作业提交模板（Copy & Paste）

### 3.1 标准作业脚本 `run.sbatch`

```bash
#!/usr/bin/env bash
#SBATCH -J demo                 # 作业名
#SBATCH -p a100_global          # 分区：只用 /mnt 选 global；依赖本地盘选 local
#SBATCH --gres=gpu:1            # GPU 数量（建议显式写）
#SBATCH -c 8                    # CPU 核数
#SBATCH --mem=32G               # 内存
#SBATCH -t 02:00:00             # 时长：HH:MM:SS 或 D-HH:MM:SS
#SBATCH -o logs/%x-%j.out       # 标准输出日志（%x=作业名, %j=ID）
#SBATCH -e logs/%x-%j.err       # 错误日志

set -euo pipefail
mkdir -p logs

echo "节点: $(hostname)"
echo "CUDA_VISIBLE_DEVICES=$CUDA_VISIBLE_DEVICES"
nvidia-smi -L
python3 -V

# python3 train.py ...
```

### 3.2 常见提交姿势

- 场景 A：常规训练（数据在 `/mnt`）

```bash
sbatch -p a100_global --gres=gpu:4 run.sbatch
```

- 场景 B：数据在本机本地盘（例如 `A100-0309-16900:/data/...`）

方法 1（推荐）：使用本机分区

```bash
sbatch -p a100_local_A100-0309-16900 --gres=gpu:1 run.sbatch
```

方法 2：使用 `--nodelist` 强制指定节点

```bash
sbatch --nodelist=A100-0309-16900 --gres=gpu:1 run.sbatch
```

若不确定分区名：

```bash
sinfo -o '%P %a %D %N'
```

## 4. 资源申请参数（GPU/CPU/内存/时长）

| 资源类型 | 参数 | 示例 | 备注 |
|---|---|---|---|
| GPU | `--gres=gpu:<N>` | `--gres=gpu:8` | 建议显式写，避免“抢 GPU / 看不到 GPU / 误用全部 GPU” |
| CPU | `-c <N>` | `-c 64` | 经验：每张 GPU 配 8–10 核起步（按任务调整） |
| 内存 | `--mem=<大小>` | `--mem=400G` | 单位 K/M/G/T |
| 时长 | `-t <时间>` | `-t 24:00:00` | 支持 `HH:MM:SS` 或 `D-HH:MM:SS` |

提示：按需申请，避免资源要太大导致排队很久。

## 5. 交互式调试（Interactive Mode）

```bash
srun -p a100_global --gres=gpu:1 -c 8 --mem=32G -t 02:00:00 --pty bash -l
```

进入后：

```bash
hostname

```

退出释放：`exit` 或 `Ctrl+D`。

## 6. 故障排查（Troubleshooting）

### Q1：作业一直 PD（Pending）？

```bash
squeue -j <jobid> -o '%.18i %.9P %.8T %.20R'
scontrol show job <jobid>
```

常见 Reason：
- `Resources`：资源不足（比如你要 8 卡，但当前没有空闲 8 卡节点）。
- `Priority`：正在排队。
- `ReqNodeNotAvail`：你指定的节点不可用/维护中。

### Q2：看不到 GPU，或 GPU 数量不对？

```bash
echo "CUDA_VISIBLE_DEVICES=$CUDA_VISIBLE_DEVICES"
nvidia-smi -L
```

如果没写 `--gres=gpu:N`，Slurm 可能不会为你分配/限制 GPU（不同环境行为可能不同）。

### Q3：报错 “No such file or directory”，疑似读不到数据？

高概率：脚本里用了 `/data` 或 `/data2`，但作业被调度到了另一台机器。

解决：
- 把数据迁移到 `/mnt`，然后用 `a100_global`；
- 或明确使用 `a100_local_<节点名>` / `--nodelist=<节点名>`。

### Q4：`squeue` 里用户变成 nobody，或 `srun` 报 Error generating job credential？

原因：多节点环境下账号 UID/GID 不一致，导致 Slurm 识别异常。

自查：

```bash
id
id -u
```

如果你有 jobid，再看作业侧 UserId 是否异常：

```bash
scontrol show job <jobid> | egrep 'JobId=|UserId=|GroupId=|JobState=|Reason='
```

处理建议：
- 先退出并重新登录一次，再重试提交；
- 仍失败：把 jobid、上面 `scontrol show job` 输出里 `UserId=` 那一行、以及 `id` 的输出发给管理员。

管理员侧详细排查/修复记录：
- `docs/developer/ops/slurm_a100/issues/20260204_huangjianuo_srun_credential_nobody_uid_mismatch.md`
- `docs/developer/ops/slurm_a100/issues/20260204_zhouqm_begintime_credential_stdout.md`

## 7. 使用规范（Dos and Don'ts）

- 建议把日志/输出写到 `/mnt`（便于跨节点查看），例如：`-o /mnt/.../logs/%x-%j.out`
- 不确定资源需求时，先用小资源 `srun --pty` 验证，再提交长作业
- 避免在登录 shell 长期跑重负载任务；请用 `sbatch`/`srun` 走调度
