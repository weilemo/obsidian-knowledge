## 当前结论

- 主结论应只使用 MB32：`HRQ all int2 identity`、`HRQ TK8 int4+int2 identity` 与 BF16 都基本追平。当前 `HRQ all int2 identity` 为 `0.7635`，BF16 为 `0.7633`，差值 `+0.0001`；该差异极小，应按同口径近似持平解读，不应解读为量化稳定优于 BF16。
- `HRQ all int2 identity` 将 KV cache 从 BF16 的 `49.36 GB` 降到 `10.38 GB`，节省约 `79.0%`；peak memory 从 `63.40 GB` 降到 `24.66 GB`。
- `HRQ TK8 int4+int2 identity` 与 BF16 基本追平，`0.7616 vs 0.7633`，差值为 `-0.0017`，同时 KV cache 从 `49.36 GB` 降到 `14.07 GB`，节省 `71.5%`。
- `ours-identity-quick15` 与 `HRQ TK8 int4+int2 identity` 是同一方法的不同评估口径；Quick15 分数不能直接拿来和 BF16 MB32 比。
- `affine_channel` 虽然降低预量化 residual Rel-L2，但 Quick15/q12 的 VBench final 明显下降，暂不作为默认预测器。
- 截图四项需要补齐 prompt set、VBench 配置、KV cache 和日志来源；目前只能作为参考。

## 已完成实验：all-HRQ-int2 MB32

记录时间：2026-06-04 20:14 CST；结果更新时间：2026-06-05 12:47 CST

当前状态：已在 `forcing_1` 跑完 MB32 生成与 VBench 8 维评估，并按项目聚合公式完成总分计算。

### 实验目的

补一个不使用 head-wise mixed precision 的 uniform HRQ int2 baseline，用来回答：

- HRQ 的收益到底来自 temporal residual quantization 本身，还是来自 head-wise top-k mixed precision？
- 在更激进的全 2-bit HRQ 下，质量是否比 packed/topk int4+int2 更稳？
- 如果 all-HRQ-int2 已经接近 HRQ TK8 int4+int2，则 head-wise 机制的边际收益有限；如果明显下降，则说明 top-k 保护重要 heads 是必要的。

### 聚合与判据

评估完成后，需要用 `scripts/eval/aggregate_results.py` 的同一套 min/max 与 `2:2:1` 权重聚合。因为现有脚本 label 列表是 hard-coded，建议在跑完后新增 `hrq_all_int2_mb32` label，或者写一个只读取该目录的临时聚合脚本。

主比较对象：

| 对照 | 目的 |
|---|---|
| BF16 Baseline MB32 | 看全 HRQ int2 的绝对质量损失 |
| packed TK8 int4+int2 MB32 | 看 uniform HRQ int2 是否胜过 packed mixed precision |
| HRQ TK8 int4+int2 identity MB32 | 看 head-wise top-k mixed precision 的边际收益 |
| packed TK4/TK8 int4+int2 MB32 | 看 HRQ residual quantization 是否整体更抗低比特 |

预期解释：

- 若 `HRQ all int2 identity` 接近 `HRQ TK8 int4+int2 identity`，说明 HRQ residual quantization 本身贡献很大，head-wise top-k 保护不是必要条件。
- 若 `HRQ all int2 identity` 明显低于 `HRQ TK8 int4+int2 identity`，但仍高于 packed TK8 int4+int2，说明 HRQ 有效，但重要 heads 仍需要高 bit 保护。
- 若 `HRQ all int2 identity` 低于 packed TK8 int4+int2，说明全 2-bit residual quantization 过激，后续应聚焦 mixed precision。
