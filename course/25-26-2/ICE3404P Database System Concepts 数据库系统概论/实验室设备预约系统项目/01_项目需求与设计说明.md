# 01. 项目需求与设计说明

## 1. 项目目标

构建一个真实场景的实验室设备预约数据库系统。
重点不是前端，而是把规则放在数据库层保证一致性。

## 2. 角色与核心流程

角色：
- 普通用户（学生/老师）：查询设备、发起预约、签到签退
- 管理员（实验员）：管理设备、维护工单、处理违约

流程：
1. 用户查看设备可用状态
2. 提交预约（设备 + 时间段）
3. 系统校验规则（冲突、资格、设备状态）
4. 成功预约后进行签到/签退
5. 若违约则自动记录违约信息

## 3. 核心业务规则

1. 预约时间必须满足 `start_time < end_time`
2. 同一设备在同一时段不允许重叠预约
3. 维护中的设备不能预约
4. 需要资质的设备，用户必须有有效资质
5. 单用户同时有效预约数量不超过 2 条
6. 违约状态（`no_show`）自动生成违约记录

## 4. 关系设计（3NF 思路）

- `users` 只存用户信息
- `devices` 只存设备信息，实验室信息拆分到 `labs`
- `reservations` 只表达“谁在何时预约了哪台设备”
- 签到日志、维护工单、资质、违约记录拆为独立表，避免冗余和更新异常

这样设计后：
- 插入异常减少：新增设备不需要先写预约
- 删除异常减少：删除预约不影响设备主数据
- 更新异常减少：设备属性只改 `devices` 一处

## 5. 为什么可用于中期汇报

- E-R 关系清晰（实体边界明确）
- 逻辑到 Schema 的映射可追踪
- 触发器可直接演示“错误数据写不进去”
