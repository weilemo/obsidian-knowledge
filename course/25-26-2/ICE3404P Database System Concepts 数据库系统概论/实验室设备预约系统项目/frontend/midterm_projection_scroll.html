1. 背景与需求

先定义真实业务问题，再提炼核心规则，这是整个数据库设计的起点。

项目背景

实验室预约场景经常出现预约冲突、资质不匹配、维护占用期间误预约。我的目标是把这些规则固化到数据库，避免只依赖应用层校验。

  • 角色：普通用户（学生/老师）+ 管理员（实验员）
  • 流程：查设备 -> 提交预约 -> 校验规则 -> 使用设备 -> 记录结果
  • 原则：任何入口写库都必须经过同一套规则

关键业务规则

start_time < end_time 同设备同时间段不可重叠 维护/离线设备不可预约 需资质设备必须通过校验 单用户有效预约上限 2 条
讲解建议：这部分可先说“规则是什么”，后面每一节都对应这些规则如何被实现。

2. E-R 设计

把业务对象和关系抽象成 E-R 结构，建立从需求到 Schema 的桥梁。

实体分层

users

用户信息与角色

devices

设备状态与资质要求

reservations

预约主记录

labs

实验室归属

user_device_certifications

用户-设备资质桥接

maintenance_orders

维护工单

checkin_logs

签到签退记录

violation_records

违约记录

关系基数主线

  • lab 1:N devices：实验室管理多台设备
  • user 1:N reservations：用户可以发起多条预约
  • device 1:N reservations：设备会被多次预约
  • user N:M device：通过资质表实现多对多
讲解建议：先讲 users-devices-reservations 三表主链路，再补资质、维护、签到和违约模块。

3. Schema 与 3NF

E-R 转关系模式后，通过主外键和约束确保结构化正确性与一致性。

关系模式摘要

表 主键 / 外键 核心约束 作用
users PK: user_id CHECK(role), UNIQUE(email) 用户主数据
devices PK: device_id, FK: lab_id CHECK(status), CHECK(requires_cert) 设备与状态
reservations PK: reservation_id, FK: user_id/device_id CHECK(status) 预约过程数据
maintenance_orders PK: order_id, FK: device_id/created_by CHECK(status) 维护流程
violation_records PK: violation_id, FK: reservation_id/user_id UNIQUE(reservation_id, violation_type) 违约追踪
3NF 解释：主数据与过程数据分离，非主属性不依赖其他非主属性，减少冗余和更新异常。

4. DB 层逻辑下沉

数据库对象分工明确：约束保底线、触发器保流程、视图保口径。

约束（CHECK / FK）

控制字段值域和跨表引用一致性，防止脏数据和孤儿数据进入系统。

触发器（TRIGGER）

实现业务规则：冲突校验、资质校验、维护冲突、no_show 自动违约。

视图（VIEW）

提供统一查询出口：可用设备总览、用户预约统计、未来预约明细。

规则执行链路

  • 预约写入前：先校验时间合法，再检查冲突、资质和维护工单。
  • 签到签退后：自动更新预约状态。
  • 标记 no_show 后：自动新增违约记录，保证可追踪。
一句话总结：规则由数据库强制执行，而不是由应用“尽量”执行。
