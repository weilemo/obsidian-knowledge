项目背景

实验室预约场景中最常见的问题是：同设备时间冲突、用户资质不足、维护期间误预约。项目目标是把这些规则写进数据库层，让任何入口写数据都遵守同一套规则。

  • 角色：普通用户（学生/老师）+ 管理员（实验员）
  • 流程：查设备 -> 提交预约 -> 校验规则 -> 使用设备 -> 记录结果
  • 重点：不依赖前端也能保证数据正确性

关键业务规则

start_time < end_time 同设备时间段不可重叠 维护设备不可预约 需资质设备必须校验 单用户有效预约上限 2 条
一句话可讲：先定义业务规则，再落地到 E-R 和 Schema，最后由 DB 对规则进行强制执行。

关系基数与设计主线

  • lab 1:N devices：一个实验室管理多台设备
  • user 1:N reservations：一个用户可发起多次预约
  • device 1:N reservations：一台设备可对应多条预约记录
  • user N:M device：通过资质表实现多对多关系
讲法建议：先讲主链路 users-devices-reservations，再讲规则增强模块（资质、维护、签到、违约）。

关系 Schema 与规范化说明（3NF）

表 主键 / 外键 核心约束 作用
users PK: user_id CHECK(role), UNIQUE(email) 用户主数据
devices PK: device_id, FK: lab_id CHECK(status), CHECK(requires_cert) 设备与状态
reservations PK: reservation_id, FK: user_id/device_id CHECK(status) 预约过程数据
maintenance_orders PK: order_id, FK: device_id/created_by CHECK(status) 维护流程
violation_records PK: violation_id, FK: reservation_id/user_id UNIQUE(reservation_id, violation_type) 违约追踪
3NF 解释：主数据与过程数据分离，非主属性不依赖其他非主属性，减少冗余与更新异常。

DB 层逻辑下沉方式（对应 SQL 已实现）

约束（CHECK / FK）

负责底线合法性：状态枚举、字段值域、跨表引用正确，避免脏数据和孤儿数据。

触发器（TRIGGER）

负责流程规则：冲突校验、资质校验、维护冲突、no_show 自动记违约。

视图（VIEW）

负责查询口径统一：可用设备总览、用户预约统计、未来预约明细。

  • 预约写入时：先校验时间合法，再检查冲突、资质、维护工单。
  • 签到/签退后：触发器自动更新预约状态。
  • 标记 no_show 后：自动写入违约记录，保证可追踪。
这页一句话总结：规则在数据库层被强制执行，任何入口写入都不能绕过。
