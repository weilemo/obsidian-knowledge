# 05. 中期汇报 PPT（5页可直接贴）

## 第1页 项目背景与目标（25秒）

### 页面标题
实验室设备预约系统：数据库设计中期汇报

### 页面内容
- 真实场景：实验室设备预约经常存在冲突、资质遗漏、维护占用问题
- 项目目标：构建一个“规则由数据库强制保证”的预约系统
- 本次范围：需求分析、E-R 图、关系 Schema、DB 层逻辑设计

### 讲稿
我的项目是实验室设备预约系统。这个场景里最常见的问题是预约冲突、资质不匹配和维护期间误预约。我的目标是把这些规则下沉到数据库层，通过主外键、约束、视图和触发器统一保证数据正确。本次中期重点汇报设计，不展示前端系统。

## 第2页 需求分析与业务规则（45秒）

### 页面标题
需求分析：角色、流程、规则

### 页面内容
- 角色
  - 普通用户（学生/老师）：查询设备、提交预约、签到签退
  - 管理员（实验员）：设备维护、工单管理、违约处理
- 核心流程：查设备 -> 提交预约 -> 校验规则 -> 使用设备 -> 记录结果
- 关键规则
  - `start_time < end_time`
  - 同设备同时间段不可重叠预约
  - 维护/离线设备不可预约
  - 需资质设备必须先通过资质校验
  - 单用户同时有效预约数不超过2

### 讲稿
我先从业务需求出发，而不是先建表。系统有普通用户和管理员两类角色，主流程是查设备、预约、使用、记录。接着把关键规则明确下来，比如时间合法、不能重叠预约、维护不可约和资质校验。这些规则后续都由数据库层直接执行。

## 第3页 E-R 图设计（70秒）

### 页面标题
E-R 图：从业务对象到关系

### 页面内容
- 核心主线实体
  - `users` 用户
  - `devices` 设备
  - `reservations` 预约
- 增强规则实体
  - `labs` 实验室
  - `user_device_certifications` 用户设备资质
  - `maintenance_orders` 维护工单
  - `checkin_logs` 签到日志
  - `violation_records` 违约记录
- 关键关系
  - `lab 1:N devices`
  - `user 1:N reservations`
  - `device 1:N reservations`
  - `user N:M device` 通过资质桥接表实现

### 讲稿
E-R 图里我先保证主业务链路清晰，也就是用户、设备、预约三者关系。然后把规则相关信息拆分成独立实体，比如资质、维护、签到和违约。这样设计后，每个实体职责单一，关系清晰，后续映射到关系模式时也能稳定满足规范化要求。

## 第4页 关系 Schema 与规范化（65秒）

### 页面标题
Schema 设计与 3NF 说明

### 页面内容
- 主键与外键
  - 每张表主键唯一标识记录
  - 通过外键保证跨表引用正确
- 约束设计
  - `CHECK` 限制状态枚举和值域
  - `UNIQUE` 防止重复资质记录
  - 外键避免孤儿数据
- 规范化说明（3NF）
  - 主数据与过程数据分离
  - 非主属性不依赖其他非主属性
  - 降低冗余，减少更新异常
- 索引设计
  - 预约冲突路径索引：`(device_id, start_time, end_time, status)`
  - 用户查询路径索引：`(user_id, status, start_time)`

### 讲稿
在关系设计阶段，我重点做了三件事：第一是主外键完整性，第二是约束设计，第三是规范化。我的表结构满足3NF，主数据和过程数据分开，避免冗余和更新异常。针对高频场景我也加了索引，尤其是设备时间段冲突和用户预约查询路径。

## 第5页 DB层逻辑与后续计划（45秒）

### 页面标题
DB层实现思路与里程碑

### 页面内容
- DB 层逻辑下沉方式
  - 视图：`vw_device_available_now`、`vw_user_reservation_summary`
  - 触发器：冲突校验、资质校验、维护冲突校验、no_show 自动违约记录
  - 约束：时间和状态合法性
- 中期后计划
  - 补充测试数据与异常用例
  - 增加演示脚本，展示非法写入被数据库拒绝
  - 完成最终验收 Demo（建库 -> 插数 -> 查询 -> 规则拦截）

### 讲稿
我的核心设计理念是把规则放到数据库层，而不是放在应用层。通过视图统一查询口径，通过触发器拦截非法写入，通过约束保证字段合法，这样任何入口写入都必须遵守同一套规则。中期后我会补全测试和演示链路，保证最终验收时可完整展示设计有效性。
